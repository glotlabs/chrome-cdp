# chrome-cdp — Vision, Architecture and Roadmap to v1

Status: DRAFT (iterate on this first; every other plan depends on it)

## 1. Problem

Coding agents that need to look at or test a web page usually reach for
Playwright (library, `playwright-cli`, or Playwright MCP). That works, but it is
built for humans writing test code, not agents issuing one command at a time:

- **Heavy install.** Node runtime, npm package, and a patched browser download.
  This is slow and brittle in sandboxes and CI.
- **Not built for stateless calls.** An agent runs one shell command per step.
  The library wants a long-lived script, and MCP ties you to one client.
- **Token-hungry output.** Full snapshots after every action and verbose stack
  traces cost context.
- **Indirection.** Playwright's protocol layer hides CDP, so it is hard to reach
  the raw power when needed.

## 2. Product statement

`chrome-cdp` is a single static binary that drives Chrome/Chromium over the
Chrome DevTools Protocol. It is designed first for AI agents and second for
humans. It is **the best tool for an agent to open, inspect, operate and verify
a web page from a shell.**

### Design principles (tie-breakers for every decision)

1. **One command = one step.** Every command is a fast, stateless-looking CLI
   call. State (browser, tabs, refs, logs) lives in a background daemon.
2. **Agent-legible output.** The default output is compact and deterministic
   plain text built to minimise tokens. `--json` is available everywhere for
   machines.
3. **Refs over selectors.** `snapshot` returns an accessibility tree with short
   refs (`e12`). Actions take refs. CSS, text, role and XPath locators are also
   supported.
4. **Auto-wait, never sleep.** Every action waits for actionability, and
   navigation waits for load. Agents should never need `sleep`.
5. **Errors that teach.** Every error says what happened, why, and the next
   command to run.
6. **Zero-config, but escapable.** It finds or installs Chrome by itself. Raw
   CDP (`chrome-cdp cdp Domain.method '{...}'`) is always one command away.
7. **Linux and macOS are first-class.** Both run in CI on every commit, on both
   amd64 and arm64.
8. **Secure by default.** It launches Chrome with `--remote-debugging-pipe`, so
   no TCP port is opened. Profiles are isolated, and the daemon socket is
   user-only (0600).

## 3. Key technical decisions (proposed; revisit in review)

| Decision | Choice | Why |
|---|---|---|
| Language | **Rust** (stable, edition 2024, MSRV pinned in `rust-toolchain.toml`) | Single static binary, no runtime, fast startup (<10 ms), memory safety, strong typing for the protocol. |
| Async runtime | `tokio` (the daemon runs a current-thread runtime on its main thread; see plan 02's decisions log) | Mature, has Unix sockets, process spawning with extra fds, timers, and `select!` for CDP event fan-out. |
| CDP client | **Own thin client** (`cdp` crate in the workspace): typed `serde` structs for the domains we use, plus `serde_json::Value` passthrough. Types are generated by a small `xtask` from the pinned `browser_protocol.json` / `js_protocol.json`. | `chromiumoxide`/`headless_chrome` bring their own lifecycle opinions and lag Chrome. We need about 15 domains, and generation keeps them honest. |
| Transport | `--remote-debugging-pipe` (fd 3/4, NUL-delimited JSON) for launched browsers; WebSocket (`tokio-tungstenite`) for `connect` | Pipe opens no port, gives no port collisions, and dies with the process. |
| Process model | **CLI → daemon over a Unix socket**, one daemon per *session* (`--session`, default `default`). The same binary runs as `chrome-cdp __daemon`. | Keeps the browser and state warm between stateless CLI calls. The daemon starts on demand and exits when idle. |
| CLI↔daemon protocol | Line-delimited JSON-RPC 2.0 (`serde`) | Simple, debuggable, and the same shape as `--json` output. |
| Snapshot source | CDP `Accessibility` domain, with a DOM-walker fallback (decided by benchmark in plan 04) | Real browser-computed roles and names. |
| Browser | System Chrome/Chromium → else Chrome for Testing downloaded by `chrome-cdp install` | Works offline if Chrome is present, and is reproducible if not. |
| CLI framework | `clap` v4 (derive) + `clap_complete` | Standard, gives shell completions and good help. |
| Errors / logging | `thiserror` in library crates, `anyhow` only at the binary edge; `tracing` for daemon logs | Typed error kinds map to exit codes and hints (plan 08). |
| TLS / HTTP for installer | `reqwest` with `rustls` (no OpenSSL) | Keeps the binary static on Linux (musl) and macOS. |
| Minimum Chrome | Current stable − 4 majors | Needed for modern headless, `Input.insertText`, and pipe transport. |

## 4. Architecture

```
┌──────────────┐  unix socket (JSON-RPC)  ┌─────────────────────────────┐  CDP pipe/ws  ┌────────┐
│ chrome-cdp   │ ───────────────────────▶ │ chrome-cdp daemon (session) │ ────────────▶ │ Chrome │
│ (CLI, short- │ ◀─────────────────────── │  - browser + target manager │ ◀──────────── │        │
│  lived)      │                          │  - ref registry per tab     │    events     └────────┘
└──────────────┘                          │  - console/network ring bufs│
                                          │  - route (mock) rules       │
                                          └─────────────────────────────┘
```

Cargo workspace layout (target):

```
Cargo.toml               workspace; release profile: lto = "fat", codegen-units = 1, strip = true
rust-toolchain.toml
crates/
  cdp/                   transport (pipe, ws), connection, sessions, generated typed domains
  cdp-gen/               protocol JSON → Rust types generator (run via `cargo xtask gen-cdp`)
  browser/               discovery, install (Chrome for Testing), launch flags, profiles
  engine/                the daemon's brain: target/tab manager, frames, navigation, waits,
                         snapshot + ref registry, locators, input + actionability,
                         observe (console/network/screenshots/trace), emulation, routing
  daemon/                socket server, session lifecycle, idle shutdown, RPC dispatch → engine
  protocol/              shared CLI↔daemon RPC types (serde), error kinds, exit codes
  chrome-cdp/            the binary: clap commands, RPC client, daemon autostart, renderers
xtask/                   dev tasks: gen-cdp, fixtures, bench, dist
testdata/site/           fixture web app used by integration tests (served by an in-test axum/hyper server)
tests/                   end-to-end tests driving the real binary against real Chrome
docs/                    user docs, agent skill file, plans
```

Inside `engine`, keep modules aligned to the plans: `page`, `snapshot`,
`locator`, `input`, `observe`, `emulate`, `route`. They can be split into
crates later if compile times demand it.

## 5. CLI surface (v1 target; details in each plan)

```
# lifecycle
chrome-cdp install [--channel stable|beta|headless-shell]    # plan 02
chrome-cdp open [url] [--headed] [--session s] [--profile p]  # plan 02/03
chrome-cdp connect <ws-url|port>                              # plan 02
chrome-cdp close | status | sessions                          # plan 02

# navigation & tabs
chrome-cdp goto <url> | back | forward | reload               # plan 03
chrome-cdp tabs | tab new [url] | tab <n> | tab close [n]     # plan 03
chrome-cdp wait <locator|--text t|--url u|--load|--idle|--fn js>  # plan 03

# understanding the page
chrome-cdp snapshot [--interactive] [--scope loc] [--diff]    # plan 04
chrome-cdp find <text|role:name>                              # plan 04
chrome-cdp text [loc] | html [loc] | attr <loc> <name>        # plan 04

# acting
chrome-cdp click|dblclick|hover|focus <loc>                   # plan 05
chrome-cdp fill <loc> <text> | type <text> | press <keys>     # plan 05
chrome-cdp select <loc> <value...> | check|uncheck <loc>      # plan 05
chrome-cdp upload <loc> <file...> | drag <from> <to>          # plan 05
chrome-cdp scroll [loc|--by dx,dy] | dialog accept|dismiss    # plan 05

# observing
chrome-cdp screenshot [loc] [--full] [-o file]                # plan 06
chrome-cdp pdf -o file | console | errors | network [--failed]# plan 06
chrome-cdp eval <js> | cdp <Domain.method> [json]             # plan 06
chrome-cdp trace start|stop | har start|stop                  # plan 06

# environment
chrome-cdp route <pattern> [--status --body --file --abort]   # plan 07
chrome-cdp emulate <device> | viewport WxH | geo | tz | locale | media | offline | throttle  # plan 07
chrome-cdp cookies | storage | state save|load <file>         # plan 07

# agent ergonomics & verification
chrome-cdp expect <loc> visible|hidden|text|value|count ...   # plan 09
chrome-cdp test [paths] [--backend mock|<name>] [--jobs N]   # plan 11
chrome-cdp mock use|list|log|explain|check|record|serve       # plan 11
chrome-cdp init e2e | history --as-scenario | http <M> <url> # plan 11
chrome-cdp batch < steps.txt | run script.cdp                 # plan 08
chrome-cdp help <topic> | skill                               # plan 08
```

Locator grammar (shared by all commands, defined in plan 04):
`e12` / `@e12` (ref), `css=...` or a bare string starting with `#`, `.` or `[`,
`text=Sign in`, `role=button[name="Sign in"]`, `xpath=//...`, `label=Email`,
`placeholder=...`, `testid=...`. Add `>> nth=1` to chain.

## 7. Definition of done for v1.0

- [ ] Every command in §5 is implemented, documented, and covered by integration tests on Linux and macOS (amd64 and arm64).
- [x] The Playwright parity matrix (plan 10) has no ❌ in the "agent-critical" rows.
- [ ] The agent benchmark (plan 10) shows task success rate ≥ Playwright MCP, with ≤ 50% of its tokens and faster wall-clock time.
- [ ] Cold `open https://example.com` takes < 1.5 s. A warm command round trip takes < 30 ms (p50, excluding page work).
- [ ] No crash, hang, or zombie Chrome across a 1,000-command soak test.
- [ ] Install works with one command (brew, curl script, `cargo install`/`cargo binstall`, `npx`), and `chrome-cdp install` works on both OSes.
- [ ] `examples/e2e-shop` (plan 11) passes with `--backend mock` and against its real fixture backend on every CI runner.
- [ ] `chrome-cdp skill` prints an agent skill/instructions file that has been validated with Claude Code.
- [x] The CLI output and JSON schemas are versioned and documented as stable ([docs/output.md](../output.md)).

## 8. Non-goals for v1

- Firefox or WebKit support. CDP is Chromium-only. Chromium-based Edge and
  Brave may work but are not supported.
- Unit or component testing, and a general-purpose test framework in a
  programming language. E2E testing of web apps (plan 11) **is** in scope and
  must be best-in-class: committed scenario files and mock files, run with
  `chrome-cdp test`, against a mocked or a real backend.
- Windows. Keep the code portable (no hard dependency on Unix sockets outside
  `crates/daemon/src/transport/unix.rs`), but do not test it.
- Codegen/recorder, visual regression diffing, and component testing.

## 9. How to use these plans

Each plan is written so an agent with **no prior context** can execute it:
read this overview, then plan 08 §2–§4 (output conventions), then the target
plan. Plans end with acceptance criteria and a test list. Large plans are split
into numbered milestones; each milestone is sized to fit one `.looper` task.
Update the plan's `Status:` line and tick checkboxes as work lands. Record any
deviation in a `## Decisions log` section at the bottom of the plan.
